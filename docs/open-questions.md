# Open questions

Android behavior we are unsure about across OS versions (CLAUDE.md workflow rule 7).

- **Inexact alarm delay on real devices (ADR 0004).** Resolved on the API 36 emulator: `setWindow` = +10 min in use, deferred to the Doze maintenance window when idle; chose `setWindow`. Still unmeasured (needs API 26-30 images and real OEM phones, tracked in vix): older APIs and OEM battery managers (Samsung, Xiaomi) that may kill or delay alarms further.
- **Notification permission on API 26-32.** Notifications are on by default there, but the user can switch them off in Settings without a runtime permission. Resolved: yes, Home shows the notice whenever they are off (AC2.4, checked on every resume).
- **Zone update vs. `TIMEZONE_CHANGED` delivery.** `DeviceClock` relies on Android clearing the process's cached default `TimeZone` when the zone changes, so `ZoneId.systemDefault()` follows travel. Resolved on the API 36 emulator (2026-10-09): with the app open (same pid), `cmd alarm set-timezone` Mexico City -> Tokyo -> Los Angeles each rescheduled the alarm to 09:00 in the new zone, so the cache is cleared before `ReminderReceiver` runs. Older APIs not checked.
- **Repeat reminders under Doze and OEM battery managers (ADR 0005).** `setAndAllowWhileIdle` repeats are rate-limited in Doze and given a long window; how late they arrive on an idle phone, and whether Samsung/Xiaomi battery managers drop the chain, is unmeasured. Measure with `dumpsys alarm` (normal and `deviceidle force-idle`) and on real phones alongside vix.
- **Exact alarms in Doze and on OEM phones (ADR 0006).** `setExactAndAllowWhileIdle` is exact in Doze but quota-limited per app; whether 5-minute repeats stay at 5 minutes on an idle phone, and whether Samsung/Xiaomi battery managers still delay or drop them, is unmeasured. Measure with `dumpsys alarm` under `deviceidle force-idle` and on real phones (vix).
